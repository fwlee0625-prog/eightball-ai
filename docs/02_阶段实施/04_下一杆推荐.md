# 阶段 M4：下一杆推荐

## 1. 本阶段目标
从合法球局推荐真人容易执行的目标球、方向、力度与杆法。

## 2. 开始前必须具备
完成上一阶段的验收；参照总体路线与数据字典，核对输入是否真实可得；缺少授权真实数据时先使用人工合成测试数据。

## 3. 逐项执行顺序
- [ ] **步骤 5.1**：先做目标球到袋口的几何线路与障碍检测。
- [ ] **步骤 5.2**：结合赛事规则过滤犯规。
- [ ] **步骤 5.3**：生成不同力度杆法候选。
- [ ] **步骤 5.4**：快速几何初筛，再物理精算。
- [ ] **步骤 5.5**：加入角度/力度/杆点执行误差抽样。
- [ ] **步骤 5.6**：评分进球概率、走位、防守、风险。。

## 4. 应让 AI/Codex 实现的工作
实现规则引擎、候选生成器、仿真批处理、评分器和 `POST /recommendation`；输出 Top-K、理由和失败原因；建立假设玩家能力分层。

将任务拆成每次可运行的最小提交：先定义接口和假数据，再实现主流程，再补边界测试，最后做 UI 和性能。每次提交必须记录为什么这么做。

## 5. 需要自己掌握的原理
几何瞄准点、球球切线、概率模拟、置信区间、目标函数权重与 Pareto 取舍。

要求自己能回答：本步骤输入是什么、输出是什么、依赖的假设是什么、有哪些反例、怎么验证而不是凭感觉判断？

## 6. 验收与下一阶段入口
固定球局能输出合法建议，模型参数变动可解释；有防守候选；p50/p95 单杆服务耗时记录；真人难打的长球须受惩罚。

## 7. 常见跑偏与纠正
- 第三方库接口未知时先跑官方最小示例，不凭记忆写不存在的方法。
- 失败样例必须记录，不能只展示一条成功演示。
- 和职业水平有关的结论必须基于现实的独立数据验证。
- 复杂算法不必立即引入，先把最简单可评测的基线做出来。

## 每一步的统一完成标准（DoD）
1. 代码进入版本控制，类型检查、格式化及单元测试通过。
2. 使用固定样例运行并保存输入、输出、运行环境与耗时。
3. 至少编写一条正常、一条边界、一条异常测试。
4. README 中有运行命令、重现步骤、已知限制。
5. 未达到验收标准不得把任务标记为完成；记录失败原因、后续实验。
