# 阶段 M5：清台规划与流式播放

## 1. 本阶段目标
实现多杆搜索与边规划边播放，遇到真实新状态立即重算。

## 2. 开始前必须具备
完成上一阶段的验收；参照总体路线与数据字典，核对输入是否真实可得；缺少授权真实数据时先使用人工合成测试数据。

## 3. 逐项执行顺序
- [ ] **步骤 6.1**：定义状态树、候选分支、白球走位目标、对手回合与防守。
- [ ] **步骤 6.2**：先 Beam Search 2-3 杆再 MCTS。
- [ ] **步骤 6.3**：控制计算预算。
- [ ] **步骤 6.4**：每段带 state_version/sequence。
- [ ] **步骤 6.5**：前端动画队列与缓冲/取消策略。。

## 4. 应让 AI/Codex 实现的工作
实现 Planner 预算和增量事件、WebSocket /plans/{plan_id}；Vue 画清台路线与逐杆动画；新球局创建新 plan_id，旧任务取消或结果丢弃；补断线重连。

将任务拆成每次可运行的最小提交：先定义接口和假数据，再实现主流程，再补边界测试，最后做 UI 和性能。每次提交必须记录为什么这么做。

## 5. 需要自己掌握的原理
Beam Search 与 MCTS 的适用边界；搜索爆炸、超时预算、乐观估计、状态版本与幂等。

要求自己能回答：本步骤输入是什么、输出是什么、依赖的假设是什么、有哪些反例、怎么验证而不是凭感觉判断？

## 6. 验收与下一阶段入口
可展示至少两杆；规划计算较慢时动画不伪造；真实进球变化使旧版本后续动画立即停止；断线重连不重复播放。

## 7. 常见跑偏与纠正
- 第三方库接口未知时先跑官方最小示例，不凭记忆写不存在的方法。
- 失败样例必须记录，不能只展示一条成功演示。
- 和职业水平有关的结论必须基于现实的独立数据验证。
- 复杂算法不必立即引入，先把最简单可评测的基线做出来。

## 每一步的统一完成标准（DoD）
1. 代码进入版本控制，类型检查、格式化及单元测试通过。
2. 使用固定样例运行并保存输入、输出、运行环境与耗时。
3. 至少编写一条正常、一条边界、一条异常测试。
4. README 中有运行命令、重现步骤、已知限制。
5. 未达到验收标准不得把任务标记为完成；记录失败原因、后续实验。
